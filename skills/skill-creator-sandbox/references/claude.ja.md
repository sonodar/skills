# Claude Code の環境分離

[English](claude.md) | 日本語（原本）

macOS、Claude Code 2.1.311で検証した。

## 新規のrestrictedセッションを使う

対象SKILLに足りない説明を補わせないため、作成者固有の指示、skills、設定、メモリを除外する。
製品標準の指示、同梱のskillsとプラグイン、必須の管理者ポリシーは残す。
検証した読み取り専用の手順では、作成者のプロジェクト外に新しい作業ディレクトリを用意し、次の指定でCLIの新規メインセッションを起動する。

| 指定 | 目的 |
| --- | --- |
| `--restricted` | user・project・local設定を除外し、ファイルツールのアクセス先を作業ディレクトリに限定する。 |
| `--setting-sources ""` | 上記の設定元を除外することを明示する。 |
| `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` | auto memoryを別途除外する。 |
| `--strict-mcp-config` | 明示的に渡していないMCP設定を除外する。 |
| `--tools Read,Skill` | 読み取りとSKILLのツールを用意し、コマンド実行ツールは渡さない。 |
| `--permission-mode dontAsk` | 承認が必要な操作を拒否し、検証中にアクセス範囲を広げない。 |
| `--no-session-persistence` | 検証会話を保存しない。この指定自体に指示の分離効果はない。 |

対象SKILL一式と必要な入力を作業ディレクトリへコピーし、そのSKILL.mdを読んで実行するよう明示的に依頼する。
作成時の会話をresume・continue・forkせず、`--add-dir`で作成者のホームやプロジェクトを追加しない。
これはSKILLの指示の動作検証であり、descriptionによる自動選択の検証ではない。

インストール済みCLIの実体を特定して直接起動し、渡す環境変数を列挙する。
ラッパーの変数、セッション情報、接続先の上書き、シェル設定を丸ごと引き継がない。
認証を使った実測では、既存のmacOSログインのために`HOME`、`USER`、`LOGNAME`、`SECURITYSESSIONID`を残し、システム用の`PATH`、`TMPDIR`、`DISABLE_AUTOUPDATER=1`、前述のメモリ無効化指定を加えた。
`HOME`と実行用の変数だけでは認証できず、OSのユーザー・セッションを示す3変数を一緒に残すと認証できた。
各変数が単独で必要かは未検証であり、別のOSでは必要な認証情報の渡し方が異なる場合がある。
別セッションの識別子をコピーしたり、認証情報を表示したりしない。

認証を使って検証した手順では、ログイン状態のために通常のホームを維持し、上記の指定で作成者固有の指示の読み込み元を除外する。
空のホームでも合成データによる入力チェックは通ったが、今回のテストでは既存ログインを使えなかった。
その構成を動かすために認証情報や`~/.claude`全体をコピーしない。
CLIは`~/.claude.json`と必須の管理設定を引き続き利用できる。この手順は、CLIプロセス全体からホームへのアクセスを遮断するものではない。

公式の[CLI reference](https://code.claude.com/docs/en/cli-reference)、[設定の優先順位](https://code.claude.com/docs/en/settings)、[環境変数](https://code.claude.com/docs/en/env-vars)、[権限](https://code.claude.com/docs/en/permissions)を参照する。
版が異なる場合は、インストール済みCLIのヘルプと関連する変更を確認する。

## 作成者固有の入力経路をまとめて確認する

起動時の指示、rules、個人・プロジェクトのskills、設定、フック、プラグイン、カスタムエージェント、出力スタイル、メモリ、アカウント同期skills、MCP接続、継承する環境変数をまとめて確認する。
個別ファイルを無効にするリストを増やす代わりに、これらの読み込み元を除外する構成を選ぶ。
[公式のskills文書](https://code.claude.com/docs/en/skills)では、設定元から`user`を除くとアカウントのskills同期も止まる。
検証のために日常利用中のユーザー設定で同期を無効にしない。その設定は、既存の同期skillsをtrashへ移す場合がある。

検証した版では、通常起動で合成の`.claude/skills`は読み込まれたが、独立して配置した`~/.agents/skills`とプロジェクトの`.agents/skills`は読み込まれなかった。
バイナリ内の`.agents/skills`への参照には他ツールからのインポート処理が含まれており、文字列があるだけでは起動時の検出を証明できなかった。
検出対象のskillsディレクトリからのsymlinkが`.agents`を指すことはある。
`.agents`は今後も無関係と決めず、版が変わったら検出経路を確認する。

## 起動時の入力と実行中のアクセスを検証する

検証結果を採用する前に、合成の指示の読み込み元へ、秘密情報ではない独立したランダムマーカーを置いて対照条件を実行する。
通常セッションの入力にマーカーが入ることを確認してから、restrictedセッションの実入力には入らないことを確かめる。
skillsの検出確認ではSkillツールを残す。実測では、すべてのツールを無効にするとskillsのdescriptionも消えたため、その条件では読み込み元を除外できたと誤認するおそれがある。

機械テストでは、ローカルだけで待ち受ける模擬API、偽のキー、合成ホームを使い、実際のリクエスト本文を記録した。
通常のリクエストには、グローバルCLAUDE.md、rules、個人skills、プロジェクトCLAUDE.md、プロジェクトskills、auto memory、SessionStartフックのマーカーが入った。
restrictedのリクエストにはどれも入らず、標準skillsとbuiltin由来のプラグインは残った。
入力を記録するだけの模擬APIは意図的にAPIエラーを返した。その実行を動作検証の成功とは数えていない。
診断用エンドポイントへ本物の認証情報や個人のコンテキストを送らない。

実行中の確認では、作業内の読み取り成功と、作業外の読み取り拒否の両方を確認し、作業内から外へ向くsymlinkも試す。
模擬APIから実際のCLIへ決められたRead呼び出しを返すと、CLIは作業内のファイル内容と、作業外のCLAUDE.md、`.agents`内のSKILL、symlinkに対するエラーを`tool_result`として返した。
モデルの要約ではなく、これらのツール結果で境界を確認した。

その後、既存ログインによる実際のメインセッションで、コピーした対象SKILLをReadで読み、そのファイル内にだけ書いたランダムな応答を厳密に返すことも確認した。
終了コードは0で、成功を示すresultイベントが出た。
標準出力、標準エラー、デバッグログ、実際のツール結果、起動設定、マーカーの照合結果を一か所に保存する。
実行記録には`--output-format stream-json --verbose`、診断には`--debug-file`を使う。
ユーザーに長いコマンドを渡す場合は、実際のパスを埋めた起動コマンドをスクリプトに置き、短い実行方法を示す。

`InstructionsLoaded`フックやinitの一覧も参考になるが、どちらか一方だけではすべての入力が除外されたと証明できない。
指示の読み取りによってはフックが発火せず、一覧にあるプラグインが有効とも限らない。
最終応答にマーカーがないこと、マーカーの開示を拒否したこと、対象SKILLが期待どおりの出力を返したことだけで分離できたと判定しない。

## 利用できる能力と検証範囲

検証済みの手順は、ReadとSkillで対象SKILLを明示的に読み込む場合を対象とする。
書き込み、コマンド実行、MCP、サブエージェントなどが必要なら、明示された依存先だけを渡し、その能力の入力・アクセス経路も検証してから結果を採用する。
特に`--restricted`でも、`--tools`で指定すればコマンド実行ツールを追加できる。ファイルツールの制限だけではシェルを隔離できない。
必要な操作が拒否されたことを、対象SKILLの不具合と扱わない。

API入力の直接確認には合成ホームと偽のAPI認証を使った。実際のOAuthセッションではRead・resultの記録と起動時の一覧を確認したが、OAuthのリクエスト全体を取得したわけではない。
カスタムプラグイン、MCPサーバー、アカウント同期skillsを、それぞれ有効な対照条件として起動するテストや、管理者ポリシーの維持の網羅的な確認はしていない。

サブエージェントを使う場合も、同じ除外・アクセス確認が通ることを条件とする。
会話履歴を渡さないことや`omitClaudeMd: true`だけでは足りない。プラグインのフックなどが別経路でコンテキストを追加できるためである。
新しいメインセッションは通常の製品プロンプトを維持するが、カスタムサブエージェントのプロンプトはそれを置き換える場合がある。
プロンプト、認証、カスタマイズの扱いの違いを確認せずに、`--bare`や`--safe-mode`へ置き換えない。
必要な検証を、除外を確認できた環境で実行できなければ依存レビューを続け、独立した動作検証は未完了と報告する。
