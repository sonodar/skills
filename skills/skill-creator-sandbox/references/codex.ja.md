# Codex の環境分離

[English](codex.md) | 日本語（原本）

macOS、Codex CLI 0.162.1で検証した。

## 検証専用の環境を使う

対象SKILLに足りない説明を作成者の指示や状態が補わないよう、それらを除外する。
製品標準の指示、同梱のskillsとプラグイン、必須の管理者ポリシーは残す。
分離の確認を通すためにskills一覧全体を隠さない。

新しいホーム、その配下に空の`CODEX_HOME`ディレクトリ、作成者のプロジェクトとは別の検証用作業ディレクトリを用意する。
作業ディレクトリには、対象SKILLと明示された入力・依存先だけをコピーする。
作成者のシェル環境を引き継ぐ代わりに、渡す環境変数を列挙して新規プロセスを起動する。
`HOME`、`CODEX_HOME`、最小限のシステム用`PATH`、`TMPDIR`を設定し、その検証の認証と実行に必要な変数だけを追加する。
セッション識別子、`CODEX_SQLITE_HOME`などの状態保存先、接続先の上書き、シェル初期化の変数を、用途を確かめずに引き継がない。
インストール済みCLIの実体を特定して直接起動する。端末のラッパーがフックや追加設定を挿入することがあるためである。

`CODEX_HOME`だけの変更では足りない。実測では、日常利用している`~/.agents/skills`の一覧が残った。
`HOME`と`CODEX_HOME`を新しくし、空の作業場所と列挙した環境変数で起動すると、検証したローカルの指示とskillsはモデル入力から消え、同梱skillsは残った。
公式の[skillsの保存先](https://learn.chatgpt.com/docs/build-skills)、[環境変数](https://learn.chatgpt.com/docs/config-file/environment-variables)、[設定の読み込み順](https://learn.chatgpt.com/docs/config-file/config-basic)を参照する。

実セッションのテストでは、認証ファイルをコピーせず、`CODEX_API_KEY`によるAPIキー認証を使った。
検証環境での使用を承認された認証情報を使い、値を表示・保存しない。
認証できない場合は、日常利用中のCodexホームをコピーせず、進められない理由を報告する。
新しいホームでのChatGPTログインは未検証である。

## 実行中のファイル読み取りを制限する

ホームを空にしても、ツールが実行中に作成者のファイルを読むことまでは防げない。
実測では、`--sandbox read-only`で作業外の合成AGENTS.mdを読めた。
原則としてファイルへのアクセスを拒否し、検証用作業ディレクトリと実行に必要な領域だけを許可する権限プロファイルを使う。

読み取りだけの検証では、検証用`CODEX_HOME/config.toml`に次の設定を置いて確認した。

```toml
default_permissions = "evaluation"
approval_policy = "never"
allow_login_shell = false

[permissions.evaluation.filesystem]
":root" = "deny"
":tmpdir" = "deny"
":slash_tmp" = "deny"
":minimal" = "read"

[permissions.evaluation.filesystem.":workspace_roots"]
"." = "read"
```

設定を書いたことだけで判断せず、実際に適用されたプロファイルを確認する。
必須の管理者ポリシーも適用し、それを回避しない。
検証したプロファイルでは、CLIが同梱シェルの実行に必要なパスも許可していた。
[ファイルアクセス権限](https://learn.chatgpt.com/docs/permissions)を参照する。

書き込み、シェルの依存ツール、ネットワーク、外部連携が必要なタスクでは、明示されたタスクに必要な能力だけを許可し、その能力でも境界を再検証する。
必要な操作が拒否されたことを、SKILLの失敗と判定しない。
読み取りだけのテストで、あらゆるツール構成の分離を確認したとは扱わない。

## 動作検証の前に入力とアクセスを確かめる

入力の確認と動作検証では、実行ファイル、環境変数、作業ディレクトリ、設定を揃える。
コマンドを組み立てる前に、インストール済みCLIのヘルプを確認する。

- `codex debug prompt-input`で起動時の入力を確認する。通常起動で読み込まれることを確かめた合成マーカーと厳密に照合する。
- 有効な設定とskillsの検出結果を確認する。実測では、app-serverの`config/read`に`includeLayers=true`、`skills/list`に`forceReload=true`を指定して読み込み元とskillsを確認した。利用する版のapp-serverプロトコルに従って接続を初期化してから使う。
- 個人・プロジェクトの設定、フック、プラグイン、MCP定義、メモリ、以前のセッション情報を新しい保存先へ持ち込んでいないか確認する。システム設定は別途適用される場合がある。
- 作業内外の合成ファイルで読み取りを試す。この版では、`codex sandbox -P evaluation --include-managed-config -C <workspace> /bin/cat <fixture>`で、モデルの応答を介さずプロファイルを直接検証できた。

sandboxの直接実行では、作業内のファイルは読め、`/private/tmp`と元のホーム配下に置いた作業外の合成ファイルは両方とも拒否された。
拒否時の終了コードは1で、`Operation not permitted`が出力された。
モデルも同じ拒否を報告したが、execのJSONには拒否されたコマンドのイベントがなかったため、その応答は証拠として採用しなかった。
実際のsandboxプロセスの結果か、記録されたツール結果で確かめる。

すべての確認が通ったら、作業ディレクトリから新規の`codex exec --skip-git-repo-check --ephemeral --json`セッションを起動し、コピーした対象SKILLを読むよう依頼する。
検証済みプロファイルを維持し、`--sandbox read-only`に置き換えない。
実際の引数、秘密情報を除いた環境変数の説明、設定、入力の確認結果、標準出力、標準エラー、ツール結果を保存する。
ユーザーに長い起動コマンドを渡す場合は、実際のパスを埋めたコマンドをスクリプトに置き、短い実行方法を示す。

## サブエージェントと検証範囲

`fork_turns="none"`は親の会話履歴を渡さない指定であり、AGENTS.md、メモリ、skills、開発者指示の除外までは確認できない。
実際の入力と利用可能な能力について同じ確認が通る場合だけ、サブエージェントを使う。
既存履歴のforkや`queue`による送信では、独立した検証環境を作れない。

新しいホームでも、標準skillsは残り、公式プラグインカタログが取得された。
これらは作成者固有の情報ではないため、除外する必要はない。
この端末では個人・システムの設定レイヤーが空であることを確認したが、すべてのMDM・クラウドポリシーや、フック・プラグイン・MCPごとの有効な対照条件までは検証していない。
検証した能力と残る作成者固有の入力を記録し、すべてのファイル・ネットワーク経路を網羅したとは言わない。
除外を確認できなければ依存レビューを続け、独立した動作検証は未完了と報告する。
